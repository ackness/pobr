本文规定 PoBR 数据的长期架构：三个仓库的职责、数据进入 PoBR 的方式、身份与存储边界、

## 1. 目标与三仓库职责

PoBR 的游戏与语言数据只来自两个自有数据仓库的不可变发布，只在本地实物测试、CI 和发版时按固定身份临时导入。
PoBR Git 不保存数据副本。上游未及时实现的字段和修正由拥有它的仓库维护，
不以 PoB2 或 RePoE 当前的覆盖范围限制产品能力。

| 仓库 | 唯一主要职责 | 边界 |
| --- | --- | --- |
| [ackness/repoe](https://github.com/ackness/repoe) | 客户端资源解码、游戏事实和关系导出、通用字段补全、版本化数据产物及来源记录 | 不实现 PoBR 的伤害计算、敌人场景默认值或构筑配置语义 |
| [ackness/poe2-zh-cn-stats](https://github.com/ackness/poe2-zh-cn-stats) | 国服/国际服词条模板、必要的术语补充、匹配来源和人工修正 | 不以翻译替代游戏 stat 身份；现有词条库不冒充完整游戏名词库 |
| [ackness/pobr](https://github.com/ackness/pobr) | 统一接入、领域规范化、数据筛选、Rust 语义与计算、玩家使用流程和数据包发布 | Rust/Web 消费 PoBR 数据契约，不直接拼接多个站点的私有格式 |

- **自有规则留在 PoBR。** `data/overlay-common/` 中入库的规则、`pipeline/policies/` 的领域解释政策和
  Rust 规则表达构筑语义，属于 PoBR 的职责，不迁往数据仓库。
- **PoB2 只作测试参考。** `vendor/` 的固定检出供 oracle、parity、`compare`／`triage` 与构筑码兼容使用，
  不作为生产数据的写入来源。仍保留的 PoB2 解释按字段登记在
  [与 PoB2 的差异](pob2-differences.md#数据来源现状与退出顺序)，逐项退出。
- **不另建第四个数据镜像仓库。** 沿用社区已发布数据作初始输入时，标为固定社区产物，不声称已由我们从客户端完整重生。
- **统一的是身份、入口、契约和责任。** 每个事实域只有一个明确生产者；核对源不在运行时覆盖主源，
  补充项必须有出处和优先级。同一字段出现不同值时，先核对服别、补丁、单位和作用域，再按证据决定，
  不做多数投票或最后写入者获胜。人工修正绑定实体与字段、适用版本、原值预期、理由和证据；升级后原值不符时重新审查。

### 1.1 跨仓问题归属

统一架构不要求合并仓库。修复放在拥有该事实或契约的一层，其他仓库只更新固定产物与消费接线：

| 问题 | 首要修改位置 | 下游责任 |
| --- | --- | --- |
| DAT/CSD/PSG 解码、原始槽位、关系、字节范围或未知字段丢失 | RePoE 及其固定 schema/解码依赖 | PoBR 更新产物 pin，并验证领域转换 |
| 交易模板配对、译文冲突、人工补译、客户端描述的语言候选 | 翻译库；原始 CSD 转录缺陷先在 RePoE 修复 | PoBR 更新固定语言产物、匹配与显示回退，不复制第二张人工工作表 |
| 稳定 ID 适配、单位/作用域解释、stat 映射、构筑准入和数值 | PoBR adapter、Rust 规则与构筑层 | CLI/WASM/Web 验证同一契约和来源归因 |
| 已有译文未消费、属性标签遗漏、语言切换或显示分组 | PoBR 显示接线 | 保留原始导入文本；不为 UI 缺陷改写事实或重做翻译采集 |

翻译来源分为交易模板、客户端原始描述、固定名词/说明词典和人工策展，不能互相冒充。
PoBR 可将固定外部词典转换为只读显示资产，但须保留来源修订、原文、文件摘要、生成命令和缺译原因；
新增人工补译归回翻译库。按技能 ID 连接时仍核对完整原文与版本，同名、近似文本或字形转换不算同一来源证据。

## 2. 数据流与导入时机

```text
RePoE 发布 ───┐
              ├─► PoBR 组合锁 ─► 临时导入（按摘要校验、可缓存）─► 领域 adapter 与组包
翻译库发布 ───┘                                                        │
                       CLI／WASM／Web ◄─ GameData／BuildData ◄─ schema-3 运行包
```

| 场景 | 导入方式 |
| --- | --- |
| 本地实物测试与开发 | `mise run data:prepare` 按组合导入到忽略的 `data/<版本>/`；下载按摘要缓存在 `.cache/`，可离线重放 |
| CI | 需要实物数据的作业临时导入；下载缓存只用于加速，命中后仍逐文件校验摘要 |
| 发版 | tag 触发完整验证，发布同次构建的 CLI／WASM／Web 产物；数据随产物分发，不回写 Git |
| 纯 fixture 测试 | 只读声明的合成夹具，不导入 owner 数据 |

默认导入只读取 owner 仓库的精确 Git revision，不读同级 checkout 或可变分支内容。
尚未发布的 owner 交付只能用显式的本地文件参数提供，并且仍须匹配锁中的摘要；这条路径只用于发布前的验证，不能产生正式组合。
缺失、摘要不符或未声明的输入直接失败，不回退到旧快照、旧 artifact 或较早的"最新"结果；离线模式只使用已认证缓存。

## 3. 发布与导入契约

- **owner 发布。** 每个 owner 在默认分支的 `publication/index.json`（`owned-data-publication-index/v2`）登记通道序号，
  指向不可变的 release 描述（`owned-data-publication/v2`）。描述按角色列出精确 revision、路径、大小和 SHA-256：
  RePoE 提供游戏、制作、普通事实、显示来源、来源校验器和测试夹具；翻译库提供语言、显示目录与库、审核补译、
  工作台、辅助说明和语言生成，并声明它绑定的 RePoE 显示来源。序号单调递增、前驱精确；分叉、回退和缺角色都是错误。
- **组合锁。** [`pipeline/latest/data-composition.json`](../pipeline/latest/data-composition.json) 是 PoBR 唯一的数据输入声明，
  包括每个 owner 的一次 publication、目标游戏／补丁／服别／语言、PoBR 自有共享规则与需求文件的 pin，以及期望的运行身份。
  同补丁修订用 generation 和前驱摘要区分。导入脚本的输入应由组合与 owner 描述派生；
  过渡期的分域锁由组合按字节固定，不能单独修改。
- **身份。** schema-3 `manifest.json` 列出全部运行文件及 SHA-256，未列出的文件视为不存在；
  `GameData::identity()` 标识快照、共享覆盖层和有效 patch，并进入计算结果的 `provenance`。
  完整快照与紧凑 release 是不同投影，身份分别记录，不能互换。
- **回滚。** 回滚单位是完整组合，恢复后核验身份，不能只回退版本目录或 `CURRENT`。
  目标形态是另一份组合；owner 尚未发布对应描述时使用冻结的旧版锁。
  用户 `patch/` 是单独的本地覆盖身份，回滚后重新校验，不兼容时拒绝该组合并保留原文件。
- **owner 代码。** 需要运行 owner 提供的生成或校验代码时，只按 pin 取回声明的文件并校验字节；
  运行包不携带这些代码，收据保留其身份。

## 4. 存储边界

| 内容 | 位置 | Git |
| --- | --- | --- |
| 代码、契约、组合锁与需求、来源接受记录 | `crates/`、`tools/`、`pipeline/` | 跟踪 |
| PoBR 自有规则与领域政策 | `data/overlay-common/` 中的自有文件、`pipeline/policies/` | 跟踪 |
| 活动版本标记 | `data/CURRENT` | 跟踪 |
| 小型合成夹具 | 各 crate 与工具的 `tests/fixtures/` | 跟踪 |
| 运行快照 | `data/<版本>/` | 忽略 |
| owner 提供的共享输入 | `data/overlay-common/` 中的外部文件 | 忽略 |
| 下载缓存、候选与报告 | `.cache/` | 忽略 |
| Web 同步数据、导入的测试夹具与辅助说明 | `web/public/data/`、`web/src/fixtures/`、`web/src/lib/supportDescriptions.zh-CN.json` | 忽略 |
| PoB2 参考检出 | `vendor/` | 忽略 |

- `pipeline/imports/check_data_ownership.py` 只允许 `data/` 下跟踪 `CURRENT` 和锁中声明的自有共享规则。
- 导入后工作树必须保持干净；出现未忽略的新文件，说明忽略规则漏项或脚本写错了位置，应当失败。
- 发布产物可随应用分发，但不因此成为 Git 内的数据副本；PoBR 自己的 artifact 也不能替代外部事实或语言库。
- 已移除的快照不改写 Git 历史，也不作生产回退。调查报告与机器测量放在 `.cache/` 或仓库外，不作为来源锁。

## 5. 更新、采用与发布

1. **owner 生产。** RePoE 与翻译库按固定来源生产、运行各自的完整 guard、发布不可变描述后推进索引。PoBR 不代为生产。
2. **发现与冻结。** `mise run data:latest check|resolve` 读取两个索引并冻结候选组合。
   官方版本观察只说明端点公布的版本；owner 尚无完整新发布时报告缺口，保留现有默认。
3. **验证。** 候选在精确 head 上通过 PR gate 和 Full gate：完整快照、普通领域生产、显示侧表、
   完整与紧凑投影等价，以及同次构建的 WASM 消费最终包。
4. **采用。** 组合锁经受保护的 PR 合并更新。本地安装用 `data:update` 显式选择，并携带期望的旧身份做 CAS；
   源码合并不自动切换 `CURRENT`。
5. **发版与部署。** 发版 tag 重新运行完整验证并发布同次产物；数据采用不会自动触发发版。

无人值守的提案与采用需要两项托管条件：仓库 secret `DATA_SYNC_TOKEN`（contents、pull requests 和 Actions 权限，
并可读取分支保护），以及 master 对管理员同样生效的严格 required `PR gate`。缺少任一项时控制器报告原因并保留默认；
提交工作流文件本身不代表这些条件已经启用。细节见[最新发布同步](../pipeline/latest/latest-data.md)。

每次失败都保留上一套已验证数据。不用版本字符串、源码合并日期或部分新表冒充完整更新；
翻译未变化时可复用旧修订，不为每个补丁制造空提交；数据修复不要求同步升级引擎，除非 schema、语义或消费者行为改变。

## 6. 来源规则

- 自有 RePoE 的主导出链是**解析官方客户端资源**（PyPoE 与社区 dat-schema），不是读取服务端数据库；
  没有证据表明它掌握服务端公式或隐藏规则，schema 与字段命名也需要验证。
- 上游 RePoE 的描述模块会实时请求交易 API。自有 RePoE 将纯客户端描述导出与可选交易关联分开：
  默认不联网，交易关联只读显式固定的响应快照，并记录 URL、服别/语言、采集时间与摘要
  （见 RePoE 的 [stat_translations 契约](https://github.com/ackness/repoe/blob/master/RePoE/docs/stat_translations.md#poe2-offline-trade-candidates)）。
  文本匹配只产生候选，trade ID 不冒充游戏 stat ID。
- 上游的已发布 JSON 未固定 RePoE/PyPoE revision，版本发现与导出分别查询资源地址；
  我们固定一次发现结果和实际输入，不凭 `exported-version.txt` 宣称可重放。

| 需要的数据 | 主来源 | 补充与核对 |
| --- | --- | --- |
| 表内 ID、数值和关系 | 对应补丁的官方 CDN 资源或同补丁本地客户端，由自有 RePoE 导出 | 固定社区原始表可作过渡输入；另一路解码抽查关键字段 |
| 天赋图成员、拓扑和布局 | 客户端 PSG、被动定义与替换表 | GGG 官方 skilltree-export 核对布局、文本和关系；精确补丁未确认时只作旁证 |
| 描述、继承属性和对象定义 | 客户端 CSD、`.it`、`.ot` 等资源 | 官方文本、维护中的社区解析工具与具体游戏观测 |
| 客户端未完整公开的内容 | 有出处的有限策展与游戏证据 | 官方 patch notes、受控实测；PoB2 只作交叉核对 |
| 交易目录和描述关联 | 官方 API 的固定原始响应快照 | 不把采集时间当游戏补丁 |
| 简中词条和术语 | 自有翻译库及经核实的国服资源 | 保留每条来源与歧义；不以繁转简冒充国服译文 |

官方公开 API 只用于其支持的功能；GGG 的数据导出说明只把天赋树列为 PoE2 游戏数据导出的例外，
客户端字节与官方支持的数据接口是不同的来源类别。第三方网站只有来源、版本、许可和接入方式明确时才进入候选，
同源转存不增加独立证据。旧补丁资源可能不再可下载，因此原始输入、schema 和导出工具的可核实归档属于持续维护能力；
不能用最新资源贴旧版本标签。

## 7. 身份与目标结构

目标按领域组织，而不是按"来自哪家工具"组织：物品与词缀、技能与品质、天赋与珠宝、角色与召唤物、
描述与本地化、规则与场景、兼容映射。复用现有类型、快照和加载器，逐域调整；目录改名不算完成架构统一。

- **主键**：优先使用游戏稳定字符串 ID；表行号只用于本次导出的外键连接。树 graph ID、定义 ID、交易 stat ID、PoB 编号各自保留，不能互换。
- **stat**：保留原始 stat ID、数值、缩放单位和来源，读取全部实际 stat 槽并正确连接外键；不能只剩英文描述再反推数值，也不为已发现节点手填数值。
- **关系**：显式表达 gem→effect→stat-set→等级/品质、item→base/mod/augment、召唤技能→实体→技能/成长等关联。
- **条件**：对象、技能分支、装备部位与条件作用域随数值保留，不能扁平化为全局加成。
- **树**：区分"被动定义存在"和"该补丁的图内实例存在"；节点、替换、别名、拓扑与几何属于同一树身份。
- **语言**：稳定 ID 与显示模板分开；缺译回退不改变计算身份。翻译库主表以完整交易 ID 加英文分支为键，trade ID 与游戏 stat 的对应只在证据充分时建立。
- **状态**：区分未知、缺失、不适用、尚未支持与已验证，不统一默认成 0、空列表或不生效。

一份包同时标识游戏、服别、客户端补丁、树修订、领域 schema、导出与适配版本和翻译修订；
同一客户端补丁可以因数据修复产生新修订，但不能覆盖既有发布物。国际服与国服的数值差异以实际输入核对，
未核实的国服资源明确标记验证边界。

技能分支迁移须同时覆盖选择与规则查询。构筑模型与 `pobr-core::skill_env` 的 `stat_set_index` 仍是 PoB 构筑码的
1-based 兼容编号（`BuildData::select_stat_set` 经 `StatSetDef::vendor_set_index` 选择），既不是表行号也不是原生分支 ID。
目标是在导入边界经固定兼容映射解析为 `GrantedEffectStatSets.Id`，内部选择、等级数据和自有规则按此查询，
导出时再还原；辅助、buff 与未选分支的作用域一并迁移，映射缺失或冲突显式诊断。

**筛选原则。** "全"指目标版本 BD 构建所需的完整定义、数值和关联，不是把全部素材送进浏览器。
原始证据保留；按公开的产品范围选择目录并保留依赖闭包；排除项各有理由；
玩家可遇到但引擎尚不支持的定义保留身份和诊断；历史构筑使用独立历史身份；筛选结果有可审阅清单，数量相同不能证明完整。

## 8. 质量目标与领域退出条件

| 目标 | 验收依据 | 不能代替验收的信号 |
| --- | --- | --- |
| 全 | 目标补丁的定义清单、所有 stat 槽与分支、关联闭包、历史与服别边界；排除项有出处，未支持项保留诊断 | 文件存在、条目数量相近、PoB 已收录 |
| 准确 | 固定原始字节和 schema；关键字段独立核对；转换、单位、作用域和受影响计算有证据 | hash 一致、同源网站相同、只与 PoB 一致 |
| 可用 | 加载后可搜索、选择、编辑、计算、保存和重开；CLI/WASM/Web 契约不变；真实输入的损失可见 | exporter 运行成功、目录可浏览 |
| 规范 | 一套领域 schema、稳定 ID、单位与空值语义、明确的 provenance/版本/服别、兼容迁移 | 换目录名、把 Lua 改成 JSON |
| 高效 | 实测包体、冷加载、峰值内存、首次与非缓存计算和批量换装 | 只测热缓存、只引用 Rust 语言性能 |

容差按字段、显示舍入和目标设备制定，并保留可重跑基线；没有证据时不承诺固定准确率或毫秒目标。
影响受支持输出的来源或数值疑点阻止对应候选激活；目录收录、字段转换和计算支持分别验收。

验收使用已收集的真实 BD 码和 benchmark／tuned／examples 语料：记录解码与导入、装备／技能／辅助／天赋／配置保留、
可计算、未支持诊断以及保存导出重开的结果，列出实际执行数与跳过原因。Holdout 只按既有 accuracy 流程测量。
同补丁同语义比较迁移前后结果；新补丁的游戏改值、旧参考差异与迁移缺陷分开报告。

| 领域 | 退出旧写入路径的条件 |
| --- | --- |
| 来源与契约 | 新原料与新补丁可持续重放；目标设备的性能预算明确 |
| 天赋 | 文本、几何、armour、资格与语言缺口关闭，范围珠宝与加点消费者通过验证 |
| 技能与物品 | 分支编码、品质作用域、charm、基底资格与完整暗金关系有证据并经消费者验证 |
| 语义与规则 | parser／config／special、stat 映射、handler 与 buff 上下文按真实输出逐项改为自有依据 |
| actor 与策展 | OT 合并与 `mod_list`、目录策展、完整召唤与暗金关系有独立依据，不由物理行齐全推定 |
| 双服与持续维护 | 专用凭据、一次真实新发布的全链演练、浏览器与部署回滚、国服身份与数值、设备性能分别验收 |

同一域验收通过后才退出旧写入路径；每域标明"自主生产""固定社区输入，依赖仍存在"或"仅参考／兼容"。
只有目标范围的再生不再读取或执行 vendor 时，才能宣称该生产依赖已退出；PoB2 oracle 与历史兼容仍可保留。
迁移按依赖顺序逐步进行，每一步保持可运行，不把源格式迁移与大量机制变化混在一起。

## 9. 维护责任与协作

上游是可同步的来源，我们的 fork 是可独立维护的生产者。通用导出修复保持小范围、便于回馈上游；
未合入的修复留在自己的修订中，升级时检查是否仍需要。独立维护还包括 PyPoE、schema 和原始资源可用性：
先固定可用版本，出现实际格式变化再维护窄补丁。原始 stat 的含义与 Rust 规则仍由 PoBR 负责。
RePoE 代码按其许可维护，游戏数据与素材的权利属于 GGG；原始大文件归档与公开产物的可分发范围分别记录。

跨仓交接至少包含：生产者提交、产物摘要与 schema、游戏补丁与服别（未知时明确保留）、改变的字段／关系／语义、
消费方所需变更、已跑检查和未验证范围。源码合并、事实发布、PoBR 采用和活动数据切换是不同动作，
不因上游合并自动执行后续动作。已有来源缺陷应在拥有它的仓库修复，而不是在 PoBR 永久增加无出处的补丁值。

已通过验收的阶段独立提交 PR，逐步合并，不等整个迁移形成一个大 PR；合并不自动启用候选。
被取代的状态在[数据现状](data-status.md)中原地更新，不在本文或其他契约中累积阶段记录。
